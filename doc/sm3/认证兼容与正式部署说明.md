# SM3 认证兼容与正式部署说明

> 当前部署请以 [17.10-sm3.3 部署说明](17.10-sm3.3部署.md) 为准：postgres 使用 SHA256，业务账号使用 SM3。
> 下文建立独立 `navicat_admin` 账号、在启动脚本覆盖健康检查的章节保留为历史方案；新镜像内置修正后的健康检查。

## Navicat 与原有认证

SM3 是新增的口令存储和 SCRAM 认证机制，SHA256、MD5 的服务器实现仍然保留。
`startup.sh` 的 `POSTGRES_PASSWORD` 只提供初始化密码，不选择其存储格式。
镜像内 `/usr/local/bin/docker-entrypoint.sh` 调用 `initdb --auth-host=scram-sm3`；
定制 initdb 在设置初始 postgres 密码前选择 SM3，并将此默认值持久化。
入口同时在 `$PGDATA/postgresql.conf` 写入 `password_encryption='scram-sm3'`。
用户当前目录挂载对应宿主机 `/data/postgres-sm3/postgresql.conf`。
这个设置影响之后的新建/重设密码，不会自动转换已有账号的校验值。
存在 `PG_VERSION` 时跳过初始化，修改启动环境变量也不会重新设置已有密码。

以 postgres 操作系统用户进入 psql 后，可分别检查生效配置和实际账号格式：

```sql
SHOW password_encryption;
SELECT name, setting, source, sourcefile, sourceline
FROM pg_settings WHERE name = 'password_encryption';
SELECT rolname, rolpassword LIKE 'SCRAM-SM3$%' AS stored_as_sm3
FROM pg_authid WHERE rolname = 'postgres';
```

当前测试镜像初始化 `postgres` 为 SM3 口令，并生成以下远程规则：

```conf
host all all 0.0.0.0/0 scram-sm3
host all all ::/0 scram-sm3
```

因此，当前连接会被要求执行 SCRAM-SM3。截图中的 Navicat 不支持这一机制，返回
`none of the server's SASL authentication mechanisms are supported`。
定制 pgJDBC 只影响加载该 JAR 的 Java 客户端，不会更新 Navicat 的连接模块。

若 Navicat 也必须执行 SCRAM-SM3，需要其 PostgreSQL 客户端认证实现支持这一机制，
具体能否替换客户端库需要厂商支持和实际验证。不能承诺仅复制一个 JAR 或动态库即可解决。

若管理连接允许 SHA256，可单独建立管理账号；业务账号继续执行 SCRAM-SM3。
一个账号目前只保存一个 `pg_authid.rolpassword`，不能直接把 SM3 校验值用于 SHA256 SCRAM。
仅改变 HBA 算法不会转换已有密码。HBA 按第一条匹配规则执行，认证失败不会继续尝试后面的规则。

### 建立独立 SHA256 管理账号

以下操作仅在确认允许管理账号使用 SHA256 后执行。进入容器本地管理连接：

```sh
docker exec -it --user postgres postgres-sm3 psql -d postgres
```

在 psql 中运行，不在 SQL 文本内填写密码：

```sql
SET password_encryption = 'scram-sha-256';
CREATE ROLE navicat_admin LOGIN;
\password navicat_admin
RESET password_encryption;
```

该账号没有自动获得超级用户或业务表权限，需按实际管理职责授权。
测试阶段，在现有远程 SM3 通配规则之前加入：

```conf
host all navicat_admin 192.168.110.28/32 scram-sha-256
```

应用账号、原 `postgres` 账号的 SM3 密码保持原样。
Navicat 使用 `navicat_admin` 连接服务器 `10.0.0.67:55432`。
角色级混合认证可由标准 PostgreSQL 客户端验证；目标 Navicat 的成功连接仍须在用户机器验收。

## Peer 报错与健康检查修正

`peer` 用于本地 Unix socket，核对操作系统用户和数据库用户名。
原镜像的健康检查以 root 执行 `pg_isready -U postgres`，因此发生 root/postgres 身份不一致。
`pg_isready` 用于判断服务器响应状态，认证失败时也可能返回成功，故此前的 healthy 不能证明登录成功。

修正后的 `run-linux.sh` 在 `docker run` 中覆盖健康检查：

```sh
--health-cmd="gosu postgres psql -X -w -h /var/run/postgresql -U postgres -d postgres -Atqc 'SELECT 1'" \
```

用户自有 `startup.sh` 也可加入这一行。它以操作系统 postgres 身份执行实际 SQL，
不需要把数据库口令写入探活命令。复用现有镜像即可，重建容器时保留原 `/data/postgres-sm3` 挂载。
这项修正不需要重新编译数据库或重新下载源码包。

检查最近一次探活：

```sh
docker inspect --format '{{json .State.Health}}' postgres-sm3
```

本地探活验证服务器和本地管理入口。业务账号的 TCP、SM3、TLS 必须用新建业务连接单独验收。

## 正式部署边界

现有镜像默认面向测试：监听所有接口、远程 HBA 覆盖所有来源，没有自动安装 TLS 证书。
SM3 认证不会加密 SQL 和查询结果。正式部署应配置服务器证书并开启 TLS，
业务 JDBC 使用 `sslmode=verify-full` 和受信任的 CA，证书名称与连接主机一致。

HBA 应替换测试通配规则，限定数据库、账号和实际来源。例如，开启 TLS 后：

```conf
local   all     all             peer
hostssl all     navicat_admin   192.168.110.28/32    scram-sha-256
hostssl appdb   sm3_app         <应用机IP/32>        scram-sm3
host    all     all             0.0.0.0/0           reject
host    all     all             ::/0                reject
```

上述数据库名、账号、来源地址须替换为实际值。若全部远程连接必须 SM3，删除 SHA256 管理例外。
保留更早的 `host all all ... scram-sm3` 会允许非 TLS 连接，不能只在它前面增加 `hostssl` 就认为已强制 TLS。

修改后用本地管理连接检查语法并通知重载，再核对服务器重载日志：

```sql
SELECT line_number, error FROM pg_hba_file_rules WHERE error IS NOT NULL;
SELECT pg_reload_conf();
```

当前版本属于定制认证实现。功能回归、异常协议和隔离 TLS 测试不能替代目标生产环境验收。
本轮在独立 Linux 容器补测 Java 8、17 各 9 项：同实例 SM3/SHA256、原版 JDBC 的 SHA256、
定制 JDBC 的 TLS `verify-full`、错误 CA/主机名/密码与非 TLS 拒绝，18 项均通过。
这证明相应协议兼容行为；尚未操作用户机器上的 Navicat。测试 TLS 也不等于国密 TLS。
正式投用还需验证实际 Java 连接池与业务压力、备份恢复、所用扩展、主从及故障切换（如有），
并对定制认证实现完成独立安全审查与后续 PostgreSQL 安全补丁维护安排。

参考：[HBA 规则](https://www.postgresql.org/docs/17/auth-pg-hba-conf.html)、
[peer](https://www.postgresql.org/docs/17/auth-peer.html)、
[pg_isready](https://www.postgresql.org/docs/17/app-pg-isready.html)、
[pgJDBC TLS](https://jdbc.postgresql.org/documentation/ssl/)。
